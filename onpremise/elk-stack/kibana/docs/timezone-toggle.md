# Kibana Dashboards — Timezone Toggle (Space Split)

Operational guide for presenting the same Kibana dashboards in both KST and CST(UTC+8) views, toggled by a single click on the top-left Space switcher. Bootstrap / apply commands live in the [dashboards/README-en.md](../dashboards/README.md) "Per-Space timezone toggle" section — this document focuses on *mechanics, extensibility, and verification*.

<br/>

## 1. Data flow (one-liner)

```
fluentd (KST ISO8601)  →  ES (UTC epoch storage)  →  Kibana per-Space view
                                                     ├── default (Asia/Seoul) ─ KST display
                                                     └── cst     (Asia/Shanghai) ─ CST display
```

- **Storage layer**: fluentd normalizes `@timestamp` to KST(+09:00) ISO8601, but ES stores it internally as UTC epoch (standard). The data is not "skewed" toward any zone.
- **Display layer**: driven by Kibana's `dateFormat:tz` Advanced Setting, configurable **per Space**.
- Therefore, for **raw time-series panels** (NU / DAU / WAU / MAU — the ones that read `@timestamp` directly), changing the view alone is enough to toggle KST/CST, and **no re-aggregation is needed**.

> ⚠️ **Cohort / retention panels are the exception — they DO need re-aggregation.** "No re-aggregation" above holds only for panels that render `@timestamp` into a zone **at query time**. A cohort is different: the transform bakes the day boundary into a date **STRING** (`active_dates`, e.g. `"2026-07-15"`) when it writes the index. `dateFormat:tz` re-renders timestamps, but it **cannot re-bucket a date string that has already been written**. So if the cst Space reuses the KST cohort objects as-is, the clock reads CST while the **day boundary stays KST**.
>
> The fix is to precompute **both** zones: the transform emits `active_dates` (KST) alongside `active_dates_cst` (Asia/Shanghai) — see [`../../elasticsearch/transforms/`](../../elasticsearch/transforms/) — and the cst Space uses **derived variants** ([`../dashboards/cst/`](../dashboards/cst/)) that read the CST twin. `default` is the single source of truth and `cst/` is generated by [`make-cst-variant.sh`](../dashboards/make-cst-variant.sh) — **never hand-edit it** (`--check` detects drift).

fluentd normalization detail: [`observability/logging/fluentd/values/dev.yaml`](../../fluentd/values/dev.yaml) lines 256–265.

## 2. What the user sees

### Switch flow

```
┌─ Kibana top-left ───────────────────────────────────────────┐
│ [≡]  [🅢 Default]  Dashboards  >  Game Retention            │   ← click the Space icon
└─────────────────────────────────────────────────────────────┘

Dropdown
┌─────────────────────┐
│ ● Default  (KST)    │   ← current
│ ○ CST              │   ← click to view the same dashboards in CST
└─────────────────────┘

URL after the switch
- KST: https://kibana.../app/dashboards#/view/<id>
- CST: https://kibana.../s/cst/app/dashboards#/view/<id>   ← /s/cst prefix
```

### Live URL rule

[`../dashboards/manifest.txt`](../dashboards/manifest.txt) is the SSOT for which dashboards exist (`apply.sh` / `export.sh` read that same file). However many environments there are, the URLs follow from the `<dashboard-id>` in the manifest's first column via the rule below, so this document does not keep a copy of the environment list.

| Space | URL shape |
|---|---|
| Default (KST view) | `http://kibana.example.com/app/dashboards#/view/<dashboard-id>` |
| CST (UTC+8 view) | `http://kibana.example.com/s/cst/app/dashboards#/view/cst-<dashboard-id>` |

> The CST dashboard ids are **slugs** carrying a `cst-` prefix (assigned by `ID_PREFIX` in [`../dashboards/make-cst-variant.sh`](../dashboards/make-cst-variant.sh)). They are reproduced identically across a cluster rebuild / re-bootstrap, so pinning these URLs in external docs, tickets, or an iframe is safe. The CST variant ndjson is `../dashboards/cst/<dashboard-id>-cst.ndjson`.

## 3. Extensibility — adding more timezones

`setup-spaces.sh --space NAME:TZ` is repeatable. `apply.sh --space-id ID` is repeatable. So adding N zones follows the same pattern.

### Example — add a JST (Japan) view

```bash
cd observability/logging/kibana/dashboards

# 1) Create the JST Space + pin tz (re-running covers existing default/cst too — idempotent)
./setup-spaces.sh \
  --space default:Asia/Seoul \
  --space cst:Asia/Shanghai \
  --space jst:Asia/Tokyo

# 2) Bootstrap dashboards + data views into the JST Space
./apply.sh --space-id jst --include-data-view

# 3) Routine sync going forward — default from the originals, cst from the generated files
./apply.sh --include-data-view --space-id default
./make-cst-variant.sh && ./apply.sh --file cst/dev-pm-retention-dashboard-cst.ndjson --space-id cst
```

> ⚠️ That bootstrap is only correct for the **raw time-series panels** (NU/DAU/WAU/MAU). To get the jst Space's **cohort / retention** right, extend the section 5 pattern: add an `active_dates_jst` / `active_days_count_jst` agg pair to the transform pivot, recreate it, and derive a data view + dashboard variant that reads those fields. Skip it and jst keeps a JST clock on a KST day boundary.

### Common IANA timezone identifiers

| Target zone | spec example | IANA id |
|---|---|---|
| Korea KST | `--space kst:Asia/Seoul` | `Asia/Seoul` |
| China CST | `--space cst:Asia/Shanghai` | `Asia/Shanghai` (or `Asia/Taipei`, `Asia/Hong_Kong`) |
| Japan JST | `--space jst:Asia/Tokyo` | `Asia/Tokyo` |
| Vietnam ICT | `--space ict:Asia/Ho_Chi_Minh` | `Asia/Ho_Chi_Minh` |
| US PST | `--space pst:America/Los_Angeles` | `America/Los_Angeles` |
| US EST | `--space est:America/New_York` | `America/New_York` |
| EU CET | `--space cet:Europe/Berlin` | `Europe/Berlin` |
| UTC | `--space utc:UTC` | `UTC` |

> The abbreviation "CST" is ambiguous between China Standard Time (UTC+8) and US Central Standard Time (UTC-6). **Always use IANA identifiers (e.g. `Asia/Shanghai`)** for the timezone value, and reserve short labels like `cst` for the Space name only.

## 4. Model — default is the single source of truth, cst is generated

In Kibana 9.x the `dashboard` / `lens` / `visualization` saved object types are **single-namespace**. That is, the same saved-object id cannot live in two Spaces — an ES-index-level constraint. Converting them to multi-namespace requires a Kibana plugin and is not feasible at the operator level (`POST /api/spaces/_update_objects_spaces` returns `"dashboard doesn't support multiple namespaces"`). `index-pattern` (data view) is the one exception — it is multi-namespace, so it can be shared across Spaces.

So:

```
repo/observability/logging/kibana/dashboards/*.ndjson   (default = single source of truth)
                       │
            ┌──────────┴───────────────┐
            ▼                          ▼
   default Space              make-cst-variant.sh
   slug IDs preserved         (KST → CST rewrite + cst- prefix)
   (dev-pm-retention-                  │
    dashboard …)                       ▼
                              cst/*.ndjson  ── generated, never hand-edit
                                       │
                                       ▼
                                  cst Space
                                  cst- prefixed slugs
                                  (cst-dev-pm-retention-dashboard …)
```

- **Edit direction**: always edit in the default Space → `./export.sh` to capture → re-run `./make-cst-variant.sh`. Editing in cst is overwritten on the next generation.
- **Redeploy**: default via `./apply.sh --include-data-view --space-id default`, cst via `./apply.sh --file cst/<file> --space-id cst`. **Do not push the same NDJSON into both** — see section 5.
- **Ids are deterministic**: the generator prefixes `cst-` and pins the cst data view id via `uuid5`, so regenerating overwrites the same objects instead of minting duplicates.
- **Storage cost**: cst objects exist as separate ES documents (multi-namespace not allowed → no sharing). Only the saved-object metadata is duplicated, not the underlying log data.

## 5. Retention day boundary — split per Space (a resolved limitation)

> This section used to document the limitation that **the cst Space's day boundary stayed on KST**. That is now resolved. Below is how, and why it had to be done this way.

**What the symptom was**: the transform's `params.tz` was pinned to a single `Asia/Seoul`, so opening the cst Space gave you CST clock times while the Daily Cohort Retention row labels and the D+N activity-day judgement still ran on **KST midnight** — the clock and the day boundary disagreed.

**The fix**: the transform precomputes **both** zones.

| Space | Cohort data view | Field read | Day boundary |
|---|---|---|---|
| `default` | `dev/qa-example-project-game-user-cohort` | `active_dates` | `Asia/Seoul` |
| `cst` | same index, separate view (`-cst`) | `active_dates_cst` | `Asia/Shanghai` |

There is still **one index** — only the runtime fields differ. The field names (`d1_live`..`d30_live`, `cohort_date`) are identical on both sides, so the **Lens** cohort panel (Daily Cohort Retention) only needs its data-view reference swapped. The **Vega** panel (Average Retention Curve), however, uses no data view (`references: []`) — it hits the index directly and inlines its own `runtime_mappings`, so its **painless must be rewritten in place**. The two panels need different surgery, which is why an `apply.sh` flag cannot cover this and a generator is required.

**Why "per-zone aggs in one transform" rather than "a transform per zone"**: the `<zone>-example-project-game-user-cohort` split that section 8 used to propose multiplies the index, the transform, and the reprocess by the number of zones. Adding `active_dates_cst` / `active_days_count_cst` as two more aggs inside the same pivot keeps a single index and still one row per user. The cost is negligible, so there is no reason to run a transform per zone.

**Caution — adding an agg is a pivot change**, so it only takes effect after the transform is stopped, deleted, recreated, and **fully reprocessed** ([`../../elasticsearch/transforms/apply.sh --replace`](../../elasticsearch/transforms/apply.sh)). The on-prem raw retention deletes at the doc level while preserving the `/users/create` anchor forever via `must_not` (`../../elasticsearch/index-retention/`), so a full reprocess recomputes `first_seen` exactly as before — it is safe.

## 6. Verifying after rollout

### A) Browser (most direct)

1. Open Kibana → click the Space icon top-left.
2. Toggle `Default` (KST) ↔ `CST` and watch the same dashboards re-render with a different timezone.
3. Time-axis labels should shift by one hour (KST 09:00 = CST 08:00).

### B) CLI — verify the Advanced Setting

```bash
PASS=$(kubectl -n logging get secret elasticsearch-es-elastic-user -o jsonpath='{.data.elastic}' | base64 -d)

# Default Space dateFormat:tz
kubectl -n logging exec -i elasticsearch-es-default-0 -c elasticsearch -- \
  curl -s -u "elastic:$PASS" -H 'x-elastic-internal-origin: Kibana' \
    "http://kibana-kb-http.logging.svc:5601/internal/kibana/settings" \
  | python3 -c "import json,sys; d=json.load(sys.stdin); print(d.get('settings',{}).get('dateFormat:tz',{}).get('userValue','(unset)'))"
# Expected: Asia/Seoul

# cst Space dateFormat:tz
kubectl -n logging exec -i elasticsearch-es-default-0 -c elasticsearch -- \
  curl -s -u "elastic:$PASS" -H 'x-elastic-internal-origin: Kibana' \
    "http://kibana-kb-http.logging.svc:5601/s/cst/internal/kibana/settings" \
  | python3 -c "import json,sys; d=json.load(sys.stdin); print(d.get('settings',{}).get('dateFormat:tz',{}).get('userValue','(unset)'))"
# Expected: Asia/Shanghai
```

### C) Verify dashboards / data views in the cst Space

```bash
PASS=$(kubectl -n logging get secret elasticsearch-es-elastic-user -o jsonpath='{.data.elastic}' | base64 -d)

kubectl -n logging exec -i elasticsearch-es-default-0 -c elasticsearch -- \
  curl -s -u "elastic:$PASS" -H 'x-elastic-internal-origin: Kibana' \
    "http://kibana-kb-http.logging.svc:5601/s/cst/api/saved_objects/_find?type=dashboard" \
  | python3 -m json.tool | grep -E 'title|"id"' | head -10

# Should list one dashboard per manifest.txt entry. IDs are 'cst-'-prefixed slugs.
```

## 7. Kibana API quick reference (useful in operations)

| Action | Endpoint | Required headers |
|---|---|---|
| Create Space | `POST /api/spaces/space` | `kbn-xsrf: true` |
| Delete Space | `DELETE /api/spaces/space/<id>` | `kbn-xsrf: true` |
| Advanced Settings GET | `GET /internal/kibana/settings` | `x-elastic-internal-origin: Kibana` (required) |
| Advanced Settings POST | `POST /internal/kibana/settings` | `x-elastic-internal-origin: Kibana` + `kbn-xsrf: true` |
| Saved-object import | `POST {SPACE_PREFIX}/api/saved_objects/_import?overwrite=true` | `kbn-xsrf: true` |
| Saved-object find | `GET {SPACE_PREFIX}/api/saved_objects/_find?type=...` | `kbn-xsrf: true` |

- `{SPACE_PREFIX}` is empty for the default Space, `/s/<id>` otherwise.
- In Kibana 8/9 the Advanced Settings endpoint moved from `/api/kibana/settings` to `/internal/kibana/settings` — the old path returns 400. The `x-elastic-internal-origin` header is required for the `/internal/` family.

## 8. Future extensions

- **Per-user default Space**: assign a Kibana role with `cst` as the default Space, so specific users/groups land in the CST view on login (they can still toggle to KST via the top-left switcher).
- **Spec-as-code zone roster**: lift `setup-spaces.sh`'s spec list into an external file / ConfigMap to manage zone additions through infra-as-code.
- **Day-boundary parity per zone**: to add another zone, extend the section 5 pattern — add an `active_dates_<zone>` / `active_days_count_<zone>` agg pair to the transform pivot, then derive a data-view variant that reads it. **Do not run a separate cohort transform per zone** (`<zone>-example-project-game-user-cohort`): that multiplies the index and the reprocess by the number of zones, whereas an extra agg pair keeps one index and still one row per user, at negligible cost.
